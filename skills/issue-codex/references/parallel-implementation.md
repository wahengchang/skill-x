# Parallel Implementation

**decompose → agent A/B/C → integrate**

把一個大工作**拆成可獨立進行的模組**，交給多個 agent 同時做，最後整合。核心是「拆解」與「整合」兩個邊界要清楚。

## 現成做法與參考

- **parallel-builder**：decompose → 平行 agent 各做模組 → integrate；它定義的是**一次整體計畫確認、給所有 agent 的共享契約、依賴分波（dependency waves）、以及最終的整合/驗證階段**，不是「每個 agent 各自 checkpoint」。

## 可萃取的原則

1. **拆解要可獨立**——每個模組的介面、輸入輸出先定義清楚，互不依賴。
2. **契約先於實作**——A、B、C 之間共享的介面/格式，必須在派工前定好，不能讓 agent 各自發明。
3. **整合是獨立步驟**——不是自動發生，要有專屬的整合與驗證階段。
4. **每個 agent 只拿自己需要的 context**——避免 context 汙染。
5. **依賴只在「真的需要」時才串**——能不依賴就不依賴，能平行就平行。

## 對照 skill 的準備

| 開 Ticket 前準備 | Ticket 內容準備 |
|---|---|
| 判定工作可拆成獨立模組 → 走這條 | Scope 列出每個子模組的邊界 |
| 先定好跨模組的介面/契約 | Requirements 寫明共享介面與格式 |
| 確認拆解後仍是「一連貫目標」 | 明確指出整合與驗證的完成條件 |

## 適用時機

- 前後端、多模組、多子系統並行開發
- 介面已清楚、只是工作量大的工作
- 需要加速、且模組間確實可解耦

> 對照 skill 三模式：`precise` 或 `open-implementation`（成果是 code）。拆單規則必須**沿用 SKILL.md 原文**：「獨立目標應拆單，**除非使用者明確要求合併**」。區分「獨立可交付的子目標」（→ 拆單）與「同一連貫交付物內、僅是解耦模組」（→ 不拆，一張 issue 內並行）。不要覆蓋掉「使用者要求合併」的例外。
